# L06 深读 · 维护、编辑和人的实际投入

本批细读八项登记来源，并沿 Microsoft Research 的研究方向补读一项新来源。下列应用为待验证的迁移假设。

### `arxiv:2412.01769`

- 原文：[Commit0: Library Generation from Scratch](https://arxiv.org/html/2412.01769v1)
- 范围：arXiv v1。细读 §§3.2–3.3、§4、§§5–6，核对 Tables 1–3、Figure 5 和两个反馈例子。
- 机制：从可定位版本中移除主要实现，保留 API、文档和测试。作者用每个库的 Docker 镜像提供可复现的运行反馈。Claude 3.5 Sonnet 的 SDE-I 在 Lite 上通过 29.3% 的单测。集成指定测试入口和静态检查命令的 OpenHands 通过 42.95%。几个开放权重模型在静态分析修订后反而退步。论文也展示了模型误读类型提示并破坏原可用生成器的例子。
- 改变的动作：在新增算子和 runtime adapter 时，用固定环境分别给 API 契约、编译反馈、边界正确性、性能数据。记录哪种反馈触发了有意义的改动，以及是否引入此前通过的回归。对长规范按变更涉及的接口和约束取证。
- 推翻条件：在同工具预算下比较全部反馈、按失败定位的反馈与最小反馈。如果额外报告增加误修或阅读成本，减少注入范围。报告中的单测通过率不能代替公开发布所需的覆盖、性能和维护性。

### `arxiv:2512.12216`

- 原文：[Training Versatile Coding Agents in Synthetic Environments](https://arxiv.org/html/2512.12216v2)
- 范围：arXiv v2。细读 §§3–4、§5.1–5.2、§6，核对 Tables 1–4 的任务组合和比较口径。
- 机制：先合成项目和任务，生成沙箱和测试，再生成实现。实现过程可读测试，终评恢复原测试文件。7B 对照中，493 条通用及问题修复轨迹对应 SWE-bench Verified 11.0% 解决率，704 条的完整混合为 17.0%。完整混合增加了问题复现和库实现，但训练数量也变化。与 R2E-Gym 相比，轨迹数更少且单条更长，文中估算训练数据约 27.5M 对 45.8M token。
- 改变的动作：用真实故障和合成变体共同建立数据来源。合成项目可把 profiler 症状定位、复现和修复拆开。在变更前冻结评估逻辑，复验时读取独立验证的工作负载。用固定训练 token 或固定预算消融样例类型，测哪类证据真正帮助完成目标任务。
- 推翻条件：若只改善合成样本，或模型学会测试特征却无法判断真实环境的偏差，保留数据作低成本开发样例。记录生成、复审和维护成本。少量长轨迹的训练效率不能直接反映总成本。

### `arxiv:2602.16819`

- 原文：[Hybrid-Gym: Training Coding Agents to Generalize Across Tasks](https://arxiv.org/html/2602.16819v1)
- 范围：arXiv v1。细读 §§2.1–2.4、§§3.1–3.3、§§4.1–4.5，核对 Tables 3–5 及 Figures 3–4。
- 机制：从常见代理动作拆出定位、依赖查询和函数生成。构建时复用两个容器镜像，Table 3 报告每条训练环境设置平均 0.07 美分，范围仅为 rollout 的环境设置。7B 的 500 条函数定位训练在 SWE-bench Verified 得 12.8%，491 条问题修复训练得 10.6%。在 Easy 50 的消融中，移除落盘编辑动作会显著影响输出补丁的任务。教师的成功轨迹也会因工具调用的回合结构而有不同蒸馏效果。
- 改变的动作：如果真实工作需要产出可运行的 benchmark 配置或带版本的修复，示例就要包含这些动作的输入、输出和反馈。用源码搜索和离线 trace 训练低成本子技能，把少量需要跑 GPU 的完整案例留作真实验收。对比工作流、few-shot 和 SFT，先量化错误发生的环节。
- 推翻条件：用同预算比较离线动作训练和直接完整任务样例。若离线组只提高定位分数，却不能选对真实测量、输出可用配置或降低维护成本，把离线任务用于开发迭代。论文的脚本及仓库层面对照依赖其基准和教师模型。

### `https://aider.chat/docs/more/edit-formats.html`

- 原文：[Aider Edit formats](https://aider.chat/docs/more/edit-formats.html)
- 范围：截至 2026-11-13 细读官方文档的 whole、diff、diff-fenced、udiff 和模型适用说明。未运行 Aider。
- 机制：whole 重写文件，直接但输出成本随文件体积增加。diff 以搜索和替换块提交局部修改。diff-fenced 把文件路径移进围栏，以适配特定模型的输出习惯。udiff 采用简化的 unified diff，文档把它与 GPT-4 Turbo 的行为问题联系起来。
- 改变的动作：将配置生成、内核实现、跨文件重构分开试编辑格式。对小配置比较整文件和局部替换。对长文件从可定位的函数或独特上下文生成补丁。单独计解析成功、应用成功、误修改、补丁大小与人工审查时间。
- 推翻条件：若模型换版后格式优势消失，或成功应用率上升但改错位置的比例上升，换回较可审查的格式。文档给出的默认格式和模型适配应随版本复核。

### `https://aider.chat/docs/unified-diffs.html`

- 原文：[Aider 的 unified diff 实验](https://aider.chat/docs/unified-diffs.html)
- 范围：细读原实验的 89 项 Python 重构、同模型格式对照、简化格式及实现说明。
- 机制：在 `gpt-4-1106-preview` 上，搜索替换格式得 20%，改用 Aider 简化 unified diff 得 61%，含省略占位注释的任务从 12 项降到 4 项。作者建议用已有训练分布常见的格式并减少格式负担。其实现用局部旧文本找位置，省去模型猜行号。
- 改变的动作：模型提交 GPU kernel patch 时，把「能写出文本」「正确应用」「通过回归」「有人能审查」分别计数。对 PTX 中近似重复的片段，使用唯一上下文和可识别的函数边界。保留差异以便追查和回滚。
- 推翻条件：固定模型和任务、只变更格式，比较补丁完整性、误命中、性能归因和审查分钟。若使用局部上下文频繁误匹配或需要人反复修正，缩小编辑范围并补验收。历史 Python 重构的提升不能换算成当前 CUDA 或 Triton 的效果。

### `https://github.com/openai/codex/blob/16ff14c266179e6a762dc8081e9dab73a96683e0/codex-rs/apply-patch/src/parser.rs`

- 原文：[Codex apply-patch parser 固定版本](https://github.com/openai/codex/blob/16ff14c266179e6a762dc8081e9dab73a96683e0/codex-rs/apply-patch/src/parser.rs)
- 范围：通过 GitHub 读取课程指定 commit 的文件片段，blob SHA 为 `c400d075a684fda29c10269aef1958a27faf90aa`。细读文件开头语法、hunk 数据结构、`parse_patch_text`、边界检查及对应测试。未核查实际文件应用模块。
- 机制：解析器把输入转换为新增、删除、更新块。更新块保留上下文、旧行、新行及文件末尾标识。解析层检查边界与结构，应用层负责检查补丁能否在当前文件系统应用。实现为模型产生的已知格式变化保留有限的宽松规则，并保留原错误以便诊断。
- 改变的动作：把调优提案的结构检查、目标版本和上下文检查、补丁应用与实验执行变成不同的可观测步骤。解析通过后仍要检查实际 diff、实验入口和基线。将可恢复格式问题的重试与代码语义冲突区分。
- 推翻条件：向测试提供真实工作中出现的合法变体、陈旧上下文和普通格式错误。若宽松处理提高解析通过率却损害意图匹配或可复核性，维持严格规则并在错误里标明如何重试。源码只支持对解析职责的判断。

### `https://www.microsoft.com/en-us/research/wp-content/uploads/2019/04/devtime-preprint-TSE19.pdf`

- 原文：[Today was a Good Day: The Daily Life of Software Developers](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/04/devtime-preprint-TSE19.pdf)
- 范围：课程所列 TSE 预印本。细读 §§4.1–4.3、§§6.1–6.3、§8，核对 Table 2 分母和样本条件。
- 机制：研究先访谈十名开发者得到活动分类，再收集 5,971 份前一个工作日的自报。Table 2 的有效样本为 5,928 份，平均代码及测试读写约 84 分钟，调试修复 74 分钟，测试运行 41 分钟，会议 85 分钟。工作阶段会影响会议或中断的作用。样本来自一个组织的同一地区，数据以工作日为分析单位。
- 改变的动作：拿实际 AI Infra 工单记阶段时间，包括准备、阅读、有效实验、等待、复核、沟通、回归和重复配置。先确定最常推迟决策的步骤。比较不同工具时记录人有效投入和恢复上下文的次数，让工程师仍可决定下一步。
- 推翻条件：若模型改代码更快但总人工分钟数、返工或交接时间增加，则该辅助方式没有完成提效目标。用实际工单日志与短期自报交叉核对。文章的比例不应作为用户当前工作的预算。

### `arxiv:2603.17829`

- 原文：[CodeScout: An Effective Recipe for Reinforcement Learning of Code Search Agents](https://arxiv.org/html/2603.17829v1)
- 范围：arXiv v1。细读 §§3.1–3.4、§4.2、§§6.1–6.2 与 Appendix D，核对 Table 6 的修复、动作和 token。
- 机制：用终端搜索仓库，并用独立工具提交文件、模块、函数。奖励与历史补丁解析出的三级位置比较。SWE-bench Verified 中，CodeScout 补充定位给 4B 修复模型后，解决率由 13.40% 升到 17.20%。给 30B 模型后由 45.20% 到 46.00%，修复模型记录的平均步数从 51.00 到 48.11。历史补丁定义参考位置，主要实验是 Python。
- 改变的动作：在框架调优中先比较只读 `rg` 和局部代码读取，然后再试索引或专门的定位模型。要求候选包含路径、符号、对应运行证据、准备验证的判断。对动态分派、JIT 生成和 CUDA 扩展，用动态观测判断目标是否执行。
- 推翻条件：比较端到端成本时计入定位前置步骤。若定位只改善历史补丁命中，或读代码节约的时间被定位调用抵消，保留简单路径。再用至少一种与 Python 案例不同的技术栈查迁移边界。

## 同机构补读

- 原文：[Time Warp: The Gap Between Developers’ Ideal vs Actual Workweeks in an AI-Driven Era](https://www.microsoft.com/en-us/research/wp-content/uploads/2024/11/Time-Warp-Developer-Productivity-Study.pdf)
- 范围：Microsoft Research 从上一项延伸出的 2025 研究。本批核对摘要、§V.B 及 Table IV。新增扩展线索，未计入本批登记来源数。
- 机制：在 484 名参与者的调查中，242 份开放式回答描述希望自动化的工作。最常出现文档、环境设置及维护、测试的编写及维护，分别获 82、66、60 条标注。来源给出的是自报需求，无法直接推定具体工具的收益。
- 改变的动作：用任务记录验证这三类工作是否也阻塞 AI Infra 的判断。比较简短实验记录自动化、可复现环境模板与测试维护辅助分别减少多少人工分钟和返工。若相同问题很少复现，或自动化使审核更长，降低该类支持的投入。
