# L1–L2 · 工具调用、执行反馈和约束

本批对照工具的目的、调用方式、运行环境与效果口径。想用课程方法改善性能工程时，先问哪个动作能提高证据质量，再决定开放多少工具。

### `arxiv:2210.03629`

- 原文：[ReAct v3](https://arxiv.org/html/2210.03629v3)
- 范围：§2 的 ReAct 表示、§3.1–3.3 的问答与核验、Table 1 和 §3.3 失误分析。
- 方法与限制：把可更新的任务判断、动作和观测交替加入轨迹。HotpotQA 与 FEVER 使用能力有限的 Wikipedia 搜索接口。样本分析里，无信息搜索占 ReAct 错误案例的 23%，有的轨迹还反复执行先前动作。各任务上的 ReAct 和其他推理基线各有强项。
- 工程用法：给 profiler 调查器一个可定位原始行、按时间窗取数和重算的只读工具。比较只给原始 trace、固定提取与按观察调整三种路线。记录无信息调用、重复查询和最后选中的实验。若强检索或直接提取已提供足够事实，增加交互轮数未必有增量。

### `arxiv:2302.04761`

- 原文：[Toolformer v1](https://arxiv.org/html/2302.04761v1)
- 范围：§2 的位置采样、调用过滤与训练，§§4–5 的工具任务和消融，§7 限制。
- 方法与限制：先从提示样例采样工具调用，运行后以其结果能否降低后续 token loss 筛选。参照包括完全不调用和只给调用但不给结果。工具收益受模型大小和调用采样条件影响。其过滤依据是语言模型目标，无法直接判定一个工程动作是否值得成本。
- 工程用法：若考虑标注工具示范，保存同一决策前缀的「无调用、只有调用、带返回」三份对照，用选择下一步的正确性或返工而非输出相似度打分。无法改变判断的调用可保留作负样本。一个调用写得规范仍可能查错二进制或错误的 GPU 运行。

### `arxiv:2403.15452`

- 原文：[What Are Tools Anyway? v1](https://arxiv.org/html/2403.15452v1)
- 范围：工具定义、感知/动作/计算分类、工具组合与 evaluation 和 cost 段落。读 Table 3 的跨研究成本口径。
- 方法与限制：同一个接口的不同操作可能读取、计算或改变环境。对工具的功能、成本和调用正确性分别评价。综述汇集异质 benchmark，不能从其汇总值直接估算用户的工具收益。
- 工程用法：将解析 trace、读取运行状态、启动新作业作为三种不同操作。可先把重复的确定计算移入脚本。验证能否降低测量误读和人工时间，再开放需跨文件或跨步骤选择的读取能力。以终态与实际动作历史检查产生的后果。

### `arxiv:2402.01030`

- 原文：[Executable Code Actions Elicit Better LLM Agents v4](https://arxiv.org/html/2402.01030v4)
- 范围：§§2–3 的执行反馈与不同动作接口比较，§4 的训练和泛化，Appendix A.7–A.8 及 Llama2 变体说明。
- 方法与结果：可执行 Python 允许一次动作组合多个工具并复用结果，异常可作为反馈。作者在 MINT、M³ToolEval 等任务检验。Mistral 微调变体在 M³ToolEval 改善，Llama2 变体没有对应改善。训练语料与动作表示同时影响效果。
- 工程用法：复杂 trace join 可以比较自由 Python 与固定查询工具。冻结可访问文件和权限，核对缺行、单位、空表、重复 correlation ID 以及实际引用。若自由代码能覆盖更多陌生格式但误关联更多，先把关键不变量变为独立验证。提交云作业等状态变更走单独接口。

### `arxiv:2411.15100`

- 原文：[XGrammar v3](https://arxiv.org/html/2411.15100v3)
- 范围：§§3.1–3.5 的 token mask、pushdown automaton 和重叠，§4 的 microbenchmark 与 serving 对照，Fig. 10、Tables 1–2。
- 方法与结果：预计算依赖栈顶即可确定的 token，少数 token 运行时校验。CPU 生成 mask 与 GPU decode 重叠，在采样前同步。论文同引擎有开关对照，也有不同引擎与 grammar backend 的比较。其高倍数来自指定配置，且 CPU 压力随批量变化。
- 工程用法：把输出 schema 合法率、工具业务正确率和服务时延分别测。GPU 开销小仍可能受 CPU grammar compile 或排队影响。固定模型、tokenizer、schema 和 batch，比较冷/热 grammar、CPU mask 时间、TTFT/TPOT、以及实际状态是否正确。若 schema 已合法而选错调用，先改工具语义或证据输入。

## 沿参考继续查

从 L2 的工具分类和评估进入 [Gorilla v1](https://arxiv.org/html/2305.15334v1) 的 §3、§4.1–4.2，核对 AST 匹配、真实检索与 oracle 的差别。作者在 Torch Hub 有一组 oracle-aware 模型 67.20，而实际检索的两种条件是 40.32、61.82。AST 匹配无法单独证明工具改变了正确对象。再读 [ToolBench 原文 v1](https://arxiv.org/html/2305.16504v1) §§3–4 的 API 选择、参数填充和可执行性。按题定制的 oracle 示例有帮助，但不是部署时可用的检索基线。两篇是本批新增的交叉来源，下一轮若纳入正式索引，需保留入口、版本和范围。

这几篇共同支持把验证分成几项。输出可解析，命中正确工具和参数，环境实际执行到预期阶段，最后取得能区分解释的结果。可以用 vLLM 调度和 DeepInfer 运行恢复做只读回放，每项单独计分。若只是格式失败，优先约束生成。如果格式、命令都对但读取的不是同一次运行，先修状态记录。

## L5 的模型选择文档

### `https://developers.openai.com/api/docs/guides/latest-model`

- 原文：[OpenAI Docs · Using GPT-6](https://developers.openai.com/api/docs/guides/latest-model)
- 范围：2026-11-13 在线的模型选择、Async tool calling、reasoning effort 与 cache、提示与验证、限制和迁移检查。
- 方法与限制：异步工具允许在等待结果时继续独立工作，应用仍负责工具执行、状态及调用标识。推理强度、提示缓存、API 兼容性和模型不同都可能影响速度及质量。此页是当前产品文档，不能代替历史讲义里的版本或用户 workload 实测。
- 工程用法：固定同一日志、工具与预算，比较不同推理强度或模型的下一动作准确率、主动时间、端到端耗时和 token。若最慢阶段是等待 GPU，先评估能否并行读取独立证据。若读错运行、版本或状态，优先修工具记录，避免把模型强度作为唯一解释。
