# 多 Agent 协作、通信和评估

### `arxiv:2603.21489`

- 原文：[Effective Strategies for Asynchronous Software Engineering Agents，arXiv v2](https://arxiv.org/html/2603.21489v2)
- 范围：§2 依赖图、分配、worktree、集成和终止，§3 主结果和对照，§4 隔离及并行数消融，§6 限制。
- 方法：协调者把依赖写入有向图。仅在前置改动进入集成分支后分配依赖任务。执行者在独立 worktree 自测后提交 commit，冲突由提交方在本地解决。管理器监听完成事件并更新依赖状态。JSON 表达交付、文件和依赖。
- 证据及边界：PaperBench 的 Code-Dev 协议下，Claude Sonnet 4.5 单 Agent 57.2 分，两名执行者的 CAID 63.3 分，软隔离 55.5 分。v2 表 2 下 CAID API 成本从 3.3 增到 6.5 美元，墙钟也上升。Commit0-Lite 上从四名增加到八名反而退步。PaperBench 结果由模型评分，未运行完整评估流水线。
- 工作迁移：把框架调优拆成可单独验证的 profiler 回放、调度候选和回归测试。先锁定三者共用的运行协议和指标接口，再并行。每个工作区使用独立构建及结果目录。只有已经集成和通过测试的 commit 可以解除硬依赖。
- 最小验证：拿一个多文件框架改动和一个单文件算子改动，比较单 Agent、同目录分配、隔离工作区三个设置。固定模型及总预算。计数冲突、等待、重复 GPU 作业、集成后正确性、最终到达性能门槛的时间。若集成开销在两个任务上都盖过收益，减少需要并行修改同一产物的范围。

### `arxiv:2606.10662`

- 原文：[Decentralized Multi-Agent Systems with Shared Context，arXiv v3](https://arxiv.org/html/2606.10662v3)
- 范围：§2 共享条目、任务队列和早发布，§3 四套代码基准和消融，§4 轨迹分析，§6 限制。
- 方法：去掉常驻的中央规划者。执行者从队列排他认领任务，按发现进度发布可引用和可纠正的中间结果。条目不可改写，缺陷作为新记录追加。运行框架提供所有者及会话状态，依赖仍在执行时先做其他工作。
- 证据及边界：Terminal-Bench 4.0 的两 Agent 版本在 GPT-6-Astra、Claude Opus 5.5 两组分别达到单 Agent 的 1.54、2.02 倍速度。删掉早发布、状态可见性或共享上下文时，消融速度范围为 0.82 至 1.09 倍。ProgramBench 的两个任务在等墙钟预算下得到更高通过率。多 Agent 可消耗更多总资源，自然语言上下文也有精确聚合限制。
- 工作迁移：先公布能解锁工作的中间事实，如「回归始于某提交，复现脚本已过」或「B300 某形状发生变化，其他形状未复测」。用可追加记录保存发现、版本、影响条件和反证。让任务状态可查。把指标、时间和 artifact ID 放进结构化文件。
- 最小验证：对相同 trace 和代码快照做并行诊断，比较私聊、共享日志及共享日志加认领状态。给每项同样预算，统计重复采样、等待时间、实际成本、首次可复查诊断和最终判定。对错误的早期记录注入更正，检查旧结论是否仍被沿用。

### `arxiv:2609.21032`

- 原文：[Scaling Discovery through Test-Time Communication，arXiv v1](https://arxiv.org/html/2609.21032v1)
- 范围：§2 共享工作区和预算定义，§3 三项结果、失败路线如何被复用及验证条件，附录 A.2 协议。
- 方法：让相同模型从不同起点探索。各自保留上下文及草稿，通过追加日志分享可复现发现和反证。结果榜绑定分数、复现说明和方法来源，采用同行路线后仍保留可区分的变化。比较团队与同数量独立候选。
- 证据及边界：表 1 的多格骨牌任务团队 0.945、独立最佳 0.893。MNIST 压缩在准确率门槛下达到 1,957 字节，独立最佳 3,160 字节，投入为 96 小时等级。低预算时有通信开销，Terminal-Bench 2.0 的 team@2 优于单次尝试但未超过独立 pass@2。部分高成本结果试次少，依赖可评分的中间进展。
- 工作迁移：为可控算子任务并行探索数据布局、流水线调度和访存三个方向。发布独立可复现的正确性与性能测量，同时保留失败的机制解释。只有统一评价下稳定有益的中间改变可以被其他候选采用。保留第二种实现，便于判断收益来自哪一项。
- 最小验证：用同一模型和 GPU 时间比较独立候选加统一选择、共享中间结果的候选以及单路优化。使用同一正确性门槛、相同工作负载和独立计时。记录复用发现次数、重复实验、最终有效改善。若团队仅在更高预算下有效，按预算分别记录。

### `arxiv:2305.14325`

- 原文：[Improving Factuality and Reasoning in Language Models through Multiagent Debate，arXiv v1](https://arxiv.org/html/2305.14325v1)
- 范围：§2 独立生成与迭代更新，§3 表 1、事实任务和轮数分析，§5 与附录 A.1。
- 方法：各实例先独立生成，再读取其他实例的回答及推理后更新。比较单 Agent、反思、独立多数票和多轮交换。同一模型也能生成不同初始路径。
- 证据及边界：表 1 中三名 Agent 两轮交换，算术 81.8%，独立多数 69.0%，单 Agent 67.0%。GSM8K 分别为 85.0%、81.0%、77.0%。作者记录了共同收敛到错误答案及长对话后忽略早期内容的案例。多次生成也增加预算。
- 工作迁移：对一个有争议的性能诊断分别建立独立解释，然后交换有出处的反例。给每个解释指定不同的可测预测，例如变更 batch 规模后是 DRAM 吞吐饱和程度先变，还是 GPU 空洞先变。使用实测决定是否采纳。
- 最小验证：固定总 token 和同一组既有 trace，比较单次自检、三条独立判断、一次交换可追溯反例。统计正确改判和错误趋同，记录多读一次 trace 或跑一次小测能否以更低成本完成判定。
