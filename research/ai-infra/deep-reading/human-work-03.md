# 工作辅助的上下文、纠错与验证

L07 与 L17 的补读。以下实验是根据原文形成的待验证设想。

### `https://mypcbench.com/`

- 原文：[MyPCBench · 官方项目页](https://mypcbench.com/)
- 范围：项目主页的环境图、示例任务、工具对比、失败计数与改判说明。论文与任务 JSON 的专门阅读见其他条目。
- 方法：从同一份人设描述派生应用历史及可重新构建的环境。例如一段行程对应航班、日历、交易与邮件。对失败验收项的模型判分解释做标签计数，观察未访问必需应用、过早停止、漏填和虚构资料。
- 证据及边界：主页记录 17 个预登录网站、约 42,000 条记录和 184 个任务。在站点所用的 computer+bash 配置下，Opus 4.6 有 58.2% 的任务满分。对 Qwen 9B 的工具差异，主页记载早先明显下降在 2026 年 7 月重判后消失。榜单标签和判分应随版本保存，失败标签次数以解释为统计单位。
- 工作迁移：用一次跑测生成多个相互可核对的表示，例如 run manifest、原始 trace、汇总表和 issue 结果，并保留共同的 run ID。工具改进若只在自动评估中显著，核对验收逻辑是否将缺失证据误判成实际失败。
- 最小验证：向同一组模拟记录注入版本错配、漏查与无证据猜测三类错误。人工标一小批已知正确/错误样例，固定工具和模型，仅改判分规则，确认前后分数差能用证据解释。

### `arxiv:2505.10831`

- 原文：[Creating General User Models from Computer Use · v3](https://arxiv.org/html/2505.10831v3)
- 范围：§3、5–9 的命题与置信度、证据来源、检索与修订、两种用户研究、隐私与局限。重点核对 Table 1、Figure 5–6。
- 方法：把观察归纳为含证据、置信度和过时速率的命题。BM25 检索结合时效、去冗余和重排。新证据与旧命题一并修订，矛盾可以降低置信。Gumbo 用模型命题提供有上下文的建议，并让使用者反馈。
- 证据及边界：18 人邮件消融中，完整方案的 Brier 为 0.17 ± 0.03，去除检索为 0.36 ± 0.07，准确率分别约 76% 和 73%。完整模型排名较好，但准确率相近。短期建议研究只有一部分提议获高评分。屏幕或邮件只覆盖用户上下文的一部分，合理推断也可能超出用户希望使用的范围。
- 工作迁移：把历史经验写成有条件的实验结论，例如「某 GPU、engine 版本和负载下，调大批处理阈值改善 P99」，保留原报告。接受后续反例后更新适用范围与可信度。工作空间仅需要纳入用户允许复用的项目证据。
- 最小验证：准备同一类设置在两种 workload 上结论相反的旧记录，比较只检索全文、附条件和置信度、再支持反例修订三个方案。看新任务是否主动引用适用证据、能否正确保留两条有限结论、错误合并是否减少。

### `arxiv:2501.12326`

- 原文：[UI-TARS · v1](https://arxiv.org/html/2501.12326v1)
- 范围：§4–5 的感知和动作表示、在线轨迹构造、reflection tuning、DPO 和 System 1/2 对照。核对 Figure 7–8 及 Appendix B 的样例。
- 方法：用截图、统一动作和历史建立闭环。对执行过程中出现的错误，人工既标出错误发生前的正确动作，也标出错误已经改变状态后如何恢复。SFT 用纠正的步骤，DPO 用同状态错误和纠正动作对。思考数据的生成尝试在不给参考动作时选出能导向正确动作的解释。
- 证据及边界：§5.5 的三个域内离线基准中，单次采样的直接动作略优。多样本 Best-of-N 条件下带推理方案有优势。未见 AndroidWorld 的单次采样中，带推理更好。多样本对照依赖怎样选候选，固定预算下未必获得相同收益。
- 工作迁移：同一事故留两类训练或评估记录。一类是在执行前识别错用 profiler 或 workload，另一类是错跑之后如何恢复并重建同条件 baseline。先试参数检查或恢复流程能否覆盖，再判断是否需要标注细粒度示范。
- 最小验证：为已有的调优回放同时保留理想轨迹、错误点和错误后状态。比较完整示范、只标纠正、纠正加恢复数据，并在未见任务上比较直接执行与关键点推理的效果。验收包括错因、恢复后的正确性和重跑成本。

### `https://openai.com/index/navier-stokes-solution/`

- 原文：[OpenAI · On the Navier–Stokes Millennium Prize Problem](https://openai.com/index/navier-stokes-solution/)
- 范围：2026-09-08 公开发布全文。交叉核对其链接论文摘要和 Theorem 1.1、Lean 仓库说明及 Clay 公告。未逐行复审 166 页论证或编译 Lean 项目。
- 方法：内部模型分组探索多个问题与方法。先得 Euler 结果后转移预算，使用 Codex 整理各组中间结果并交叉注入，再由 GPT-6 Astra 进行形式化。数学主张为三维方程在特定平滑外力和初始条件下有限时间失去光滑全局解。
- 证据及边界：作者报告从启动到解约 88 小时，Lean 形式化与核验约 17 小时。对 Navier–Stokes 搜索报告约 1300 亿输出 token。作者不申领奖项，Clay 2026-09-11 的公告将结果描述为表面上已解决，正式评估另有过程。文章无单代理或同预算消融，不能据此估计并行、切换模型或交叉整理各自贡献。[Clay 公告](https://www.claymath.org/news/navier-stokes-announcement/) [Lean 证书仓库](https://github.com/openai/NavierStokesAndEuler)
- 工作迁移：在框架优化中，可从同一瓶颈并行提出不同机制的候选，例如 GPU 空闲、CPU 提交压力、通信或内存等。在中间点交换证据与失败条件，集中测能区分机制的下一组实验。最后让独立的正确性和同条件性能测试判定。
- 最小验证：在相同 GPU 时间预算下比较单路诊断、独立并行诊断、带一次中间结果交换的并行诊断。记录发现的不同机制、重复运行、有效候选、最终复核结果及总成本。若交换只增加重复，减少协调环节。
